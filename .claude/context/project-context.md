## Tech Stack

- Backend: FastAPI + async SQLAlchemy 2.0, Python, managed with `uv` (never bare `pip`/`venv`). Batch pipeline (ingest → canonicalize → validate → score) in `backend/pipeline/`.
- DB: Postgres 17. Local dev = Docker container `thesistrace-pg`; production target = Supabase (not yet provisioned).
- Migrations: Alembic, run from repo root (`db/migrations/`), not from `backend/`.
- Frontend: Next.js 16 (App Router) + Tailwind v4, semantic design tokens in `frontend/app/globals.css`.
- Deploy target (not yet live): Render (backend + cron job) + Vercel (frontend) + Supabase (DB). Cost ceiling ~$25/mo total.
- External data providers (deliberate, narrow exceptions to "no multiple providers"): SEC EDGAR (primary), Tiingo free tier (market close prices), Bank of Canada Valet API (USD/CAD FX rates, for CAD-reporting filers like CP).
- LLM: Claude Haiku 4.5, Phase 1 only — constrained rewrite of an already-computed deterministic template, never a plain wrapper doing free generation. LangGraph reserved for Phase 2 Filing Q&A only.

## Core Patterns

1. **Deterministic/LLM boundary is inviolable.** Every score/number is computed in Python, deterministically. The LLM only explains and cites an already-computed figure — it never originates one, never gives investment advice.
2. **AD-3 canonicalization tiebreak** (`backend/canonicalization/canonicalize.py`): as-originally-filed > concept-priority > decimals > fetched_at. A genuine conflict the rules can't resolve gets flagged as a `data_quality_issues` row (`needs_review`) — never silently guessed or defaulted.
3. **Tri-state signal status** (AD-16): every signal is `pass` / `fail` / `insufficient_data`. A missing input is `insufficient_data`, never a defaulted 0/false/zero.

## Security Rules

- `.env` holds `DATABASE_URL` (dev) and `TEST_DATABASE_URL` (test) as **separate** values — see Anti-Patterns below for why this must never collapse to one.

## Anti-Patterns (do NOT do)

- **Never push directly to `main`.** Every session works on its own fresh branch, merges via PR. A real git divergence happened once from two concurrent sessions pushing straight to `main` — see `CLAUDE.md`'s Git workflow section (binding, read every session).
- **Never run `pytest` with only `DATABASE_URL` set** (no `TEST_DATABASE_URL`) — the test teardown drops all tables, and it will wipe the *dev* database if the test URL isn't distinct. Real incident; documented in `.env.example`.
- **Never trust that an XBRL tag's mere existence means it covers the right fiscal years.** Different filers use different tag variants for the same concept, and some switch tags mid-history (e.g. CP switched its PP&E tag in FY2021). Always verify live, per-year coverage against real `data.sec.gov` company-facts JSON before adding a fallback mapping — the original `shares_outstanding` bug (dei cover-page date corrupting fiscal-year bucketing) was exactly this class of mistake.
- **Never treat "no XBRL tag for concept X" as automatically meaning X is zero.** It can be a genuine reclassification artifact (e.g. SHOP's convertible debt flips between `Current`/`Noncurrent` tags as it nears maturity — mapping only the Noncurrent tag would make leverage look like it swings to zero when the debt hasn't actually been repaid). When genuinely ambiguous, leave `insufficient_data` rather than force a fallback.
- **Never assume the "latest fiscal year" is the right one to surface per model.** A model can resolve for some historical years and not the most recent one (e.g. Beneish needs 8 sub-indices simultaneously); picking "latest run that exists" regardless of whether it has a value can hide real, valid results behind an unrelated newer insufficient year — see `api/repository.py`'s `get_company_overview` Verdict-selection logic.
- **No TradingView / off-the-shelf charting** — custom visualizations only (differentiates from the sibling portfolio project `equipulse`).
- **Never render a visual blend of the four models** (D12, 2026-08-27): no filled multi-axis polygon, no aggregate shape/number/grade summarizing multiple models — that is the Verdict rule applied to pixels, and Simply Wall St's snowflake is additionally design-patented. The hero glyph keeps every model's axis separate. Do not "improve" it into a snowflake.
- **Never add a writer to the batch pipeline without an idempotency key.** `pipeline/run.py` is a *daily* cron (`0 6 * * *`) over the same canonical facts, and `get_company_overview` surfaces every `data_quality_issues` row whose status isn't `dismissed`. A stage that inserts unconditionally accumulates one row per night and the UI shows the same warning N times after N days. `canonicalize_issuer` already models the pattern (skip what exists); `run_validation` had to be given it before wiring in (PR #22). Dedup must ignore status, or a `dismissed` issue gets resurrected.
- **Never let a test infer its precondition from ambient environment.** `Settings` (`app/config.py`) resolves values from the process env *and* an `.env` file (`env_file=".env"`, resolved relative to the CWD). A test asserting a var is absent passes in CI — which sets neither — while failing for anyone who sourced a real `.env`. That's deterministic-per-environment with the environments disagreeing, and green CI wrongly implies soundness. Pin both inputs: `monkeypatch.delenv(...)` **plus** neutralising the file fallback (`Settings(_env_file=None)`, or `monkeypatch.setitem(Settings.model_config, "env_file", None)` when the call is internal). See `test_health.py` and `test_verdict_explanation.py`.

## Learnings — 2026-07-29

- Real EDGAR company-facts JSON has several sharp edges, all fixed in canonicalization: `dei` cover-page facts are dated to the filing date (not FYE) and must be excluded from fiscal-year-end determination; 10-K/A amendments can carry a less reliable `fiscal_year_end` than the original 10-K; a 10-K's own "selected quarterly financial data" footnote tags quarterly sub-periods under the same accession/fiscal-year label as the true annual figure; an accounting-standard-adoption "opening balance as of Jan 1" snapshot can land in the same calendar year as the true Dec-31 closing balance. All resolved by filtering candidates to full-year-duration facts whose `period_end` matches the issuer's own recognized fiscal-year-end day (with tolerance for non-Dec-31 FYEs like OTEX's June 30).
- CP is a genuine railroad-accounting edge case: no COGS/SGA tags at all (functional expense categories instead), reports entirely in CAD (needed the Bank of Canada FX integration for Altman's X4).

## Learnings — 2026-08-01 (D8 / IFRS track)

- **IFRS is not "less comprehensive" — the mismatch is presentation, not disclosure quality.** Canadian 40-F filers tag densely (BCE 288 concepts, Cameco 250, Suncor 234, all FY2017–2025). What varies is IAS 1's allowance of expenses **by nature** vs **by function**: a by-nature filer has no SG&A line to tag at all, so Beneish's SGAI is unresolvable. Same shape as CP's missing COGS under us-gaap. Never conclude a taxonomy is unsupported from one filer — Suncor alone (2 of 4 models) would have killed D8; Cameco scores 4 of 4.
- **EDGAR XBRL for 40-F filers starts ~FY2017** — ~9 years vs OTEX's 24 under us-gaap. Fine for point-in-time scoring (needs two consecutive years) but a real constraint on the Phase-2 Growth lens's long-trend promise. Do not promise decade-plus charts for Canadian names.
- **The "tag exists but doesn't cover the years you need" trap recurs per taxonomy.** Under ifrs-full: `Revenue` can carry a single year while `RevenueFromContractsWithCustomers` (IFRS 15) carries the rest; `NumberOfSharesOutstanding` can be sparse where `NumberOfSharesIssued` is complete. Always check per-year coverage, never mere tag presence — this is the same class as the original `shares_outstanding` dei bug.
- **A caveat may annotate a score; it must never alter one.** Cameco FY2021's Beneish is +20.84 because gross margin collapsed 5.91%→0.13%, making GMI 45.1. Every input is correct and the arithmetic is right. Clamping or suppressing would be ThesisTrace originating methodology — forbidden for our own code as much as for an LLM. Presentation guards belong in the versioned formula spec, explicitly labelled as ours rather than the model author's.
- **Model-specific display logic silently applied to another model is a recurring bug class.** `bandTone()` omitted Beneish's band vocabulary; `explanation/template.py` asserted capital intensity as the reason for *every* `computed_with_caveat` run. Store the reason as data rather than inferring it from a shared enum.
- **Verify academic formulas from the PRIMARY source before encoding them — and re-verify a previous verification.** Applied twice to the same formula, with the second pass overturning the first. On 2026-08-01 a session concluded the five-factor M-score's `0.107` coefficient belongs to DEPI (not TATA as StableBread has it), citing Roxas (2011) and a secondary reproduction. Reading the Roxas original in full on 2026-08-02 showed it **contains no coefficients at all** — it applies Beneish's own model — and that it **contradicts itself** on DEPI vs TATA within three sentences. That question is OPEN, not settled; do not encode either reading. Full analysis: `_bmad-output/planning-artifacts/research-beneish-five-variable-model.md`. The general rule: a recorded "verified" claim is only as good as the source it names, so check that the cited source actually contains the thing being claimed.

## Learnings — 2026-08-04 (D8 close-out: mapping specs, golden catch-up)

- **A formula spec's `inputs` list is load-bearing, not documentation.** `scoring/runner.py` reads it to decide whether a run consumed an input that is not comparable across filers, and the methodology page publishes it. `piotroski_v1.yaml` declared 6 inputs while `scoring/piotroski.py` read 9, so the comparability caveat shipped in PR #32 could never have fired on `gross_profit`, `long_term_debt` or `revenue`. A test now asserts declared ⊇ actually-read for every model. Generalise: when a declarative list drives runtime behaviour, something must enforce that it matches the code.
- **Independent verification must not import the thing it verifies.** The golden hand-computation for the IFRS filers imports nothing from `backend/scoring` or `backend/formulas`, which is why it caught its own error rather than rubber-stamping: **Sloan uses AVERAGE total assets across two years, Beneish's TATA uses year-end.** Reusing the scoring module, or comparing only aggregates instead of every component, would have recorded a wrong figure as golden. Also confirm the guard bites — corrupting an expected value must fail the suite.
- **Spec prose has two audiences and needs two fields.** `derivations_v2.yaml` carries `note` (maintainer-facing, may cite decision records and file paths) and `rationale` (published verbatim on `/methodology`, must stand alone). The first version published "DECISION, not an identity — recorded per D8 consequence 3" to end users. Caught only by rendering the page, not by type-checking. Anything user-visible gets looked at in the browser before it ships.
- **SM-1 is a claim about the universe, so expanding the universe reopens it.** Golden coverage was closed 2026-07-29 against 4 filers; D8 grew it to 7, leaving three scored nightly with no test pinning any value. Structural tests (which models resolve) are not numeric guards. Any future filer addition must extend `phase1_golden.yaml` in the same change, or SM-1 silently stops holding.

## Learnings — 2026-08-04 (Phase 2 planning opened)

- **A superseding decision is not landed until every document it contradicts is updated in the same change.** D8 shipped IFRS support on 2026-07-29, but a week later `SPEC.md` (the *canonical contract* per CLAUDE.md) still read "Universe is fixed and US-GAAP-only" and listed "No IFRS-reporting companies" as a non-goal, and `prd.md` still deferred IFRS "indefinitely" against a universe of 4. Code, universe and golden dataset were all correct — only the contract lagged. This is dangerous precisely because BMad derives epics from SPEC + PRD: Phase 2 planning read off that contract would have produced epics for a product that no longer exists. When a decision supersedes another, grep for the superseded claim across `_bmad-output/` and fix every hit in the same commit.
- **Check whether an open question has been overtaken by events before answering it.** PRD OQ8 asked how Phase 2 should grow the universe "to 5–10 companies" — but D8 had already grown it 4 → 7 during Phase 1, using the very manual process OQ8 posed as one of its options. The question had been answered by precedent; the real decision left was only whether to keep that process. Re-read an open question against current state, not against the state it was written in.
- **Two proposed metrics can silently duplicate shipped ones.** OQ9's "receivables-vs-revenue" is substantially Beneish's DSRI and "cash-vs-earnings" substantially the Sloan accruals ratio — both already computed and displayed. Adding them would have shipped a second, differently-computed view of the same figure, creating exactly the "why do these disagree?" problem the provenance invariant exists to prevent. Before adopting a metric from an older planning doc, check it against what the models already compute.
- **`sprint-status.yaml` was unparseable by any YAML reader** from ~2026-08-02 to 2026-08-04 — an unterminated quoted string in `d8_ifrs_track` step 5's `follow_up`. Nothing caught it because the file is only ever read by humans and agents, never parsed. If you add prose to it, run `python3 -c "import yaml; yaml.safe_load(open(...))"` afterwards.
- **Phase 2 shape is D9, not the PRD's feature list.** Sequenced around one real investment decision (change detection → narrow reverse DCF → thesis journal/diff → growth → filing Q&A), with the next feature chosen from *the largest observed research failure* rather than the next list item. Epics 6–9 in `epics.md` are deliberately under-decomposed for this reason — do not "finish" them ahead of the evidence.


## Learnings — 2026-08-04 (Epic 5 implementation)

- **Rendering a page in a browser found 4 real bugs that 27 passing tests missed.** Story 5.4 alone surfaced an engine boundary defect (a first-ever run became its own predecessor, so the page reported "No change since {date}" about a comparison that never happened), a date rendering a day early west of Greenwich, silent rounding of a filed figure, and a duplicated band row. None was reachable from the API contract or a unit test. The standing rule earns its keep — treat it as mandatory, not diligence.
- **A wrong fix can still diagnose the right bug.** The first attempt at the 5.4 defect was a `has_real_prior` heuristic; it broke four existing tests, and *those failures* showed the boundary operator (`<=` vs `<`) was the actual defect. When a fix breaks unrelated tests, read the failures before reaching for a second patch.
- **Semantics that vary per model belong in the spec, not in code.** Piotroski/Altman are higher-is-better; Beneish/Sloan are LOWER-is-better because they measure risk. Encoding "improving = value rose" would have told readers that rising manipulation risk is good news. Declared per model with a citation, and a test enforces the citation.
- **The spec two-audiences trap recurs.** `trajectory_v1.yaml` stated in a YAML *comment* that its thresholds were ThesisTrace's own, but not in the machine-readable `note` — the field a reader would actually see. Same shape as the D8 `derivations_v2` bug. A comment is not a published rationale; a test caught it.

## Learnings — 2026-08-05 (post-Epic-5 hygiene + the v2 profile fix)

- **"Rule B subsumes rule A" is a claim about every input, so deleting A needs a test where the two disagree.** Story 5.7's review replaced "a schedule needs at least one middle year" with "a schedule must be contiguous from year one", recording that the latter subsumed the former. It does not: a lone year-1 bucket is a contiguous prefix of length one. The rules differ on exactly one shape, that shape was live (OTEX, six fiscal years), and it shipped a one-row "Repayment schedule" restating the near-term debt card with a different measurement basis. Spec v2 requires both, with a test on each side of the boundary. When a refactor retires a rule as redundant, the boundary case is the deliverable, not an optional extra.
- **A golden entry whose fixture cannot reproduce its own stated reason is pinning an outcome, not verifying it.** `phase1_golden.yaml` asserted `no_profile` for OTEX in every year and passed throughout, because the trimmed fixture carries none of OTEX's year-1 facts — so it structurally could not produce the shape that broke. The entry's own note had already said the fixture could not reproduce the reason; nobody drew the conclusion that the guard was therefore inert. Where a fixture cannot exercise the reason, say so **and** cover the reason somewhere that can.
- **Documentation of a rule does not hold the rule.** The same golden entry's comment read "the engine requires at least one middle year" for months after the review removed exactly that requirement. It described the intent correctly and the implementation incorrectly, and nothing connected them. This is why the profile loader now pins both admission rules as declared spec fields: the published rule and the enforced behaviour can no longer drift silently.
- **SPLIT 2026-08-20.** The 14 finding sections below moved to `engineering-findings.yaml`; `sprint-status.yaml` is now the tracker only (~260 lines) and `test_the_tracker_holds_only_tracking` keeps it that way. Findings accumulated there because `bmad-sprint-planning` REGENERATES the tracker and preserves only `action_items`, so the tracker was the one place a finding was both read every session and test-protected from the generator. It survived where it did not belong.
- **`sprint-status.yaml`'s failure mode is always "meaning parked in a comment".** Four failures now, one cause. Epic titles lived in trailing `#` comments or nowhere; the reason Epics 6-9 had no stories was prose. `epic_catalog` (added 2026-08-05) carries title + `decomposition: decomposed | deferred` + `deferred_under`/`decompose_when`, and a test requires any epic with no tracked stories to declare the deferral. Story keys are DERIVED from `### Story N.M` headings in `epics.md` — adding one to sprint-status alone fails CI, so an "inconsistency" there is usually upstream and often deliberate.
- **A value used only to decide whether to FETCH is invisible when it is wrong.** `pipeline/run.py`'s `_payload_reporting_currency` read `us-gaap` only, so it returned None for every IFRS filer and no USD/CAD rate was fetched for CCJ/BCE/SU — all three CAD reporters. Nothing broke, because `scoring/runner.py` asks the CANONICAL facts for the currency and found a rate CP had already stored for the same Dec-31 year ends. Correct by coincidence: drop CP, or add an IFRS filer with a non-Dec-31 year end, and Altman's X4 divides USD market cap by CAD liabilities. Two lessons: **two code paths answering the same question must not use different sources** (payload vs canonical facts), and a hardcoded `us-gaap` gate can survive the whole D8 sweep when its output only gates a side effect. The function had **no test at all** — check coverage on the helpers that decide what to fetch, not just on what computes.
- **A binary enum collapsed four different situations into one word.** `epic_catalog`'s `decomposition: decomposed | deferred` deferred Epics 6-9 as a block, but each had a different blocker: Epic 6 needed a data spike, Epic 7 an architecture decision (its "on return the system diffs" requires persistence, and Phase 1 has no auth), Epic 8 two design calls, Epic 9 a citation-evaluation framework that does not exist. The fix was not a third enum value — it was replacing "is this deferred?" with the per-item question **"can its acceptance criteria be written truthfully today?"** Generalise: when one flag governs several items, check whether they actually share a cause before treating the flag as the decision.
- **A gap appearing in EVERY concept at once is a method smell, not a coverage finding.** The Epic 6 spike briefly reported a uniform FY2023 gap for SHOP across capex, cash, tax, CFO and D&A. Artifact: EDGAR company-facts' `fy` field is the FILING's fiscal year, not the fact's period, so a 2023-ending fact appears under `fy=2024` and `fy=2025` as a comparative. Re-bucketing on `end` showed no gap. Real tagging gaps are concept-specific — a filer omits a line item, never an entire year of its cash-flow statement. Same fiscal-year-bucketing trap as the original `shares_outstanding` dei bug.
- **Re-canonicalizing to a new `MAPPING_VERSION` needs no EDGAR fetch.** `canonicalize_issuer` reads stored `raw_facts`, and its idempotency skip is scoped per mapping version, so a bump writes new rows rather than skipping. Verified 2026-08-05 going `concepts_v3` → `concepts_v7` on the dev DB. The debt queries filter on `mapping_version` and the score queries do not, so until that pass runs the model cards render while both debt cards silently return empty — a half-degraded page that looks healthy.

## Learnings — 2026-08-13 (Epic 6 retrospective — reverse DCF, stories 6.1–6.7 + the AD-1 fix)

- **An AD-compliance claim written in prose is not enforcement, and this is now the FIFTH instance.** `sensitivity.py`'s docstring read "Computed deterministically in Python on the write path (AD-1) — a read never triggers 35 solves". It was false the day it was written, stayed false through two stories, and became true only when PR #69 moved the computation — **without needing an edit**, which is the tell. Story 6.4's AC said "stored" and the code stored nothing. Prior four: `derivations_v2.yaml`'s `note`/`rationale`, `trajectory_v1.yaml`'s comment-not-field, the OTEX golden entry, `epic_catalog`. **Rule: if prose claims conformance to an AD, either a test enforces it or the claim is decoration.** [Source: PR #69, `backend/tests/test_reverse_dcf_store.py`]
- **The golden fixtures are TRIMMED SUBSETS, and every new capability hits that wall.** Story 6.7 found CP's fixture carried 23 us-gaap tags and neither a capex nor a cash-and-equivalents tag, so all seven filers resolved `insufficient_data` — the golden entries would have looked complete while asserting nothing about the new capability. The mappings were fine; the fixtures were the gap. Rebuild missing entries from the dev store's own `raw_facts` joined to `filings` (already-ingested real EDGAR data, keyed to accession numbers) rather than re-fetching. **Assume the next capability hits this too, and check the fixture can exercise the new concepts BEFORE writing the golden entries.** Distinct from the OTEX entry above: that was one fixture that could not reproduce its own reason; this is every fixture being blind to anything added later. [Source: `story_6_7_golden_coverage`]
- **When a standard PERMITS a choice, verify which choice each filer made from its own tags — never infer it from the standard.** IFRS lets filers classify interest paid as operating or financing, and the two IFRS filers chose differently: BCE `InterestPaidClassifiedAsOperatingActivities`, Cameco `InterestPaidClassifiedAsFinancingActivities`, both 10 years. **Consequence that survives the epic: Cameco's `cash_from_operations` EXCLUDES interest paid while every other filer's includes it, so `CFO − capex` is not the same measurement across the universe and Cameco's free cash flow reads systematically high.** Carried as versioned spec data and applied as a caveat at computation time — it annotates, never alters. [Source: `story_6_2_live_verification`]
- **An overlap-year equality proof licenses a fallback for ONE filer and must be pinned by a test.** QSR files both `CashAndCashEquivalentsAtCarryingValue` and the restricted-inclusive tag in FY2016–18 and they are identical to the dollar, which proves QSR carries no restricted cash — so the restricted-inclusive tag IS its unrestricted cash. The proof is filer-specific: a test now requires the two tags to be equal for **every** universe filer that files both, so adding a filer with real restricted cash fails loudly instead of silently inflating cash and understating enterprise value. Same technique that validated `revenue − cogs` against filers filing `GrossProfit` directly. [Source: `story_6_2_live_verification`]
- **A tag whose name contains the concept is often not the concept.** Three live traps in one epic: `CapitalExpendituresIncurredButNotYetPaid` is an accrual disclosure, not cash capex (SHOP tags it 8y, QSR 4y — the exclusion is load-bearing, not theoretical); cash-plus-restricted-cash is not cash; and the two us-gaap pre-tax-income tags differ on equity-method income and are not interchangeable. Check accrual-vs-cash and inclusive-vs-exclusive semantics before mapping, not just the name.
- **A browser spot-check only covers the code paths YOUR chosen filers exercise.** Story 6.6 was verified live against CP/OTEX/QSR/SU and looked clean; `/code-review` then found the operand label map omitted the four derivation-leaf concepts the API emits recursively — reachable only via CCJ and BCE, neither of which was in the spot-check. **Choose spot-check subjects by which code paths they exercise, not by convenience**, and treat a review after a clean visual check as complementary rather than redundant. [Source: `story_6_6_browser_verification`]
- **A NUMERIC column's scale must be chosen against the producing algorithm's tolerance, not copied from its neighbours.** The reverse-DCF solver converges to 1e-7 and returns ~26 significant digits; the codebase's usual money-shaped `NUMERIC(28,6)` would have rounded the answer **coarser than the bisection that produced it**. Rate columns are `NUMERIC(18,10)`. Two corollaries: assert the *quantization contract* rather than raw equality when comparing a stored figure to an in-memory one, and use `ROUND_HALF_UP` to match Postgres — Python's default is `ROUND_HALF_EVEN`, and the two agree on every non-tie, so the default passes indefinitely and then disagrees once. [Source: PR #69]
- **Moving computation to the write path means the feature is ABSENT until the pipeline runs.** After PR #69 a company page shows no reverse DCF until the cron has materialized that issuer. That is correct CQRS behaviour and is asserted deliberately (an unmaterialized issuer renders nothing rather than solving on the fly), but a fresh database is blank until 06:00. Any future read-path→write-path move inherits this; plan a post-deploy pipeline run rather than discovering it as a blank page.
- **A spike answers the DATA question and leaves the PRODUCT questions open.** Story 6.1 proved the operands could be assembled for 6 of 7 filers and deliberately did NOT unblock Epic 6's decomposition, because the horizon, terminal-value method, discount-rate treatment and solve target were still undecided. Do not let a green spike be read as "the epic is ready".
- **RESOLVED 2026-08-14.** `EPIC_STATUSES` now carries `blocked`, Epics 7-9 use it, and `test_blocked_status_agrees_with_the_catalog` binds it to `epic_catalog` **both ways** — a deferred epic left as `backlog` fails, and a `blocked` epic with no recorded deferral fails. Adding the enum value alone would have been a seventh instance of the same bug. Both directions were verified to fail before being declared fixed. The learning below still governs how to read the file. [Source: `test_sprint_status.py`]
- **`development_status: epic-7: backlog` READS AS "ready to pick up", and Epic 7 is not.** Its real gate lives in a different key — `epic_catalog`'s `decomposition: deferred` / `deferred_under: D9` — and `EPIC_STATUSES` has no `blocked` value, so `backlog` is the only legal thing to write. Two handovers consequently claimed "Nothing blocks Epic 7", which is false: D9 forbids selecting the next epic from list order at all; it must be chosen by the largest research failure named in a **decision packet (D10)**, and that packet is also **D3.2**, open since Phase 1. **Before planning ANY epic, check `epic_catalog`, not `development_status`.** Sibling of the four `sprint-status.yaml` failures above — one field carries the meaning, another carries the answer a reader actually sees. Consider adding a `blocked` status so the two cannot disagree. [Source: `epic_catalog`, `foundational-decisions.md` D9/D10/D3.2]

## Learnings — 2026-08-14 (the `compactAmount` boundary fix; reading a coverage gap)

- **A recorded finding's blast-radius analysis can itself be scoped to the wrong branch.** The `compactAmount` write-up measured its two options precisely — "1 input changes" vs "461 inputs change" — and closed with "no real filer figure is exactly 950,000, so nothing is broken on the page today". Both statements were true *of the millions gate*, which is the only gate it examined. The **billions** gate had the identical defect with a far wider reachable window, and it was live: CP's FY2025 Year-4 repayment bucket rendered "0.99B" in a column of "M" values, and Suncor's near-term debt *headline* read "0.97B of 9.99B". The documented case genuinely never occurs; the undocumented sibling occurred on two pages. **When a finding is scoped to one branch, boundary or filer, check its siblings for the same shape before trusting its impact assessment** — a precise measurement of the wrong thing reads exactly like a precise measurement. [Source: PR #74]
- **A gate and the display it admits values into must read the SAME quantity.** The billions gate tested one decimal (`round(abs / 1e8) / 10 >= 1`) while its branch printed two, so a value that only reaches 1.0B at one decimal was promoted and then rendered below 1 — the gate asserting "at least 1.0B" and the formatter printing "0.97B". Each branch now tests the integer count of the unit it actually renders (hundredths of a billion, tenths of a million). Generalise: **whenever a predicate decides which formatter runs, express the predicate in the formatter's own units**, or the two will eventually disagree on a boundary nobody enumerated.
- **`toFixed` breaks ties on the stored double, not half-up.** `(0.95).toFixed(1)` is `"0.9"` and `(900.05).toFixed(1)` is `"900.0"`. This is the JS sibling of the `ROUND_HALF_UP` vs `ROUND_HALF_EVEN` trap already recorded for Postgres in the Epic 6 learnings: the default agrees with the intended rounding on every non-tie, so it passes indefinitely and then disagrees once. Round explicitly (`Math.round` on the magnitude, sign reattached) rather than trusting a formatter's tie behaviour.
- **The browser check earned its keep for the sixth time**, and this instance is the strongest argument yet for the still-open Epic-4 action item ("add a live-data spot-check to the DoD"): 34 passing tests, a clean `tsc`, a clean `eslint` and a written analysis of this exact helper all missed a defect that was visible in one screenshot. Choosing the spot-check subjects by which components they exercise (CP → `MaturityProfile`, SU → `NearTermDebtShare`) rather than by convenience is what made two pages enough.
- **A deliberate mapping decision and a tag-switch defect have IDENTICAL signatures in the data — check the spec's rationale before calling one a bug.** BCE's reverse DCF resolves only to FY2023 because `CurrentPortionOfLongtermBorrowings` covers FY2016–2023 and then stops, while the wider `CurrentBorrowingsAndCurrentPortionOfNoncurrentBorrowings` runs through FY2025. That is the exact shape of CP's FY2021 PP&E switch and of the `shares_outstanding` bug, and it was one step from being reported as a defect. It is the opposite: `ifrs-full_v4.yaml:217` records a live-verified (2026-08-04) comparability decision — the wider tag exceeds the narrow one by 1.4–4.1bn in every shared year, the difference being commercial paper and securitized receivables, which the denominator excludes. "Fixing" it would have inflated BCE's ratio against every other filer while looking like a correction, and the missing years are correct `insufficient_data` under AD-16. **Before treating a coverage gap as a defect, grep the mapping spec for the concept and read the `note`, not just the mapping row.** This is why those notes carry the argument ("the wider tag includes X, which the denominator excludes") rather than merely recording the choice — a note saying "don't use tag X" would not have survived this challenge. [Source: `ifrs-full_v4.yaml:217`, `test_near_term_debt_share.py:204`]

## Learnings — 2026-08-27 (Epic 10, Story 10.2)

- **An SVG `<title>` child element causes a real React hydration mismatch — use a `title` attribute instead.** `VerdictGlyph.tsx` originally used `<title>{...}</title>` inside each axis's `<a>` for a hover tooltip. React's server-side HTML string serializer treats `<title>` specially (it doubles as HTML page metadata, normally unique-per-document in `<head>`), in a way that disagrees with how the browser's real SVG-namespace DOM parses the same tag when hydrating — a genuine, reproducible mismatch (production error #418), not a testing artifact. Confirmed by reverting just that one hunk and reproducing the error, then re-fixing it. Fixed by using a plain `title` string attribute on the `<a>` instead of a child element — no serialization ambiguity, and the anchor's accessible name still derives correctly from its own visible text content either way. Applies to any future component embedding `<title>` inside an `<svg>`, not just this one.

## Learnings — 2026-08-30 (Epic 11 planning + Codex review workflow)

- **`bmad-create-epics-and-stories`'s own first step is destructive on a mature project.** Its Step 1 copies `epics-template.md` over `{planning_artifacts}/epics.md` wholesale, then re-extracts FRs/NFRs from the PRD — built for greenfield epic generation, and it would have overwritten Epics 1–10 (47 done stories, all the `epic_catalog` deferral metadata for Epics 7-9) had it run. When adding a new epic to a project that already has a mature `epics.md`, add it by hand, matching the file's own existing conventions (`## Epic N:` summary in the Epic List, `### Story N.M:` Given/When/Then detail sections, `epic_catalog`/`development_status` entries in `sprint-status.yaml` with story keys derived via `_kebab()` in `test_sprint_status.py` — split the title on `—`/`(` first) — never invoke the skill's own generation step against an already-decomposed project.
- **Codex code review is worth the round-trip, but it consistently marks the story `done` instead of `review`.** Across two real reviews (PR #95, #96) it found genuine, verifiable issues both times — two real WCAG AA contrast failures on #95 (independently recomputed, its `4.630:1` figure was exact), and an invisible needle marker plus a missing `role="img"` on #96 (independently re-rendered and zoomed in to confirm the fix). Both times it also edited `sprint-status.yaml` to mark the story `done` while the PR was still open. This project's convention is `done` = merged to `main`, `review` = PR open (every prior epic follows this). Always re-check and correct that one field after applying Codex's fixes — verify its code changes AND audit its status-tracking edits, not just the former.

## Learnings — 2026-08-31 (Epic 11, Stories 11.3–11.8: Codex review and Term composition)

- **A reviewer's fix can be internally consistent and still wrong-direction — check which side of a reported mismatch is actually broken before applying it.** PR #101's Codex round correctly found that a `termDefinitions.ts` comment claimed Piotroski's definitions were "verbatim" from `piotroski_v1.yaml` while the code was actually adapted plain-language prose. Codex's fix made the CODE match the claim — rewriting readable "return on assets (net income ÷ total assets)" back into the spec's raw `net_income / total_assets`, reintroducing an unexplained "ROA" acronym, and deleting an explanatory clause entirely. That satisfied the comment's letter while breaking Story 11.5's own AC ("expand inline into a PLAIN-LANGUAGE definition") — the comment was the wrong side of the mismatch, not the code. Reverted the code, corrected the comment instead. When a review reports "X doesn't match Y", verify which of X/Y is actually correct before resolving toward either.
- **The same review round's two contrast findings WERE correct**, verified by independently recomputing WCAG relative luminance from the actual token hex values rather than trusting the reported ratio — matched to 3 decimal places both times. A reviewer can be right on some findings and wrong on others in the same round; one accurate finding doesn't buy blind trust for the rest.
- **Nesting an interactive element (`Term`) inside a semantically-colored container (`Badge`) is safe when status is redundantly encoded.** Badge's icon shape + background/border already carry pass/fail/insufficient-data status (AD-16's Accessibility Floor: color is never the only signal), so `Term`'s own fixed amber text color overriding just the nested label's text doesn't lose status information — confirmed live in both themes and both tones (Story 11.7, BCE + SHOP), not assumed from reasoning alone. Before assuming a color-override conflict is unsafe, check whether the information it might clobber is ALSO encoded another way (shape, position, a sibling element).

## Learnings — 2026-09-02 (`canonical_facts_amendment_gap` fix)

- **A finding's recommended option can be structurally impossible — re-derive the fix from the constraints, not from the recommendation.** The finding recommended "narrow the idempotency skip, no migration, keeps append-only". Those three cannot coexist: with a full unique key on `(issuer, concept, year, mapping_version)`, a changed winner leaves only UPDATE-in-place, which mutates a row that prior `score_inputs` reference. The recorded analysis was correct about the *bug* and wrong about the *fix*; the same care that goes into verifying a finding's reachability goes into verifying its remedy.
- **Two ADs can contradict each other silently when no live data exercises the seam.** AD-3 ranked a same-year 10-K/A as a tie with its original (→ ambiguity flag); AD-6 required the amendment's value to be what a new run references. Both were "implemented" and both were tested, and the contradiction never surfaced because no filer in the universe has an amendment carrying a value its original lacks. When a fix to one AD's mechanism does nothing observable, check whether a sibling AD's rule is what actually blocks it — here the supersession machinery was hollow until AD-3 gained rule 1a.
- **A partial unique index plus SQLAlchemy's flush order is a trap: INSERTs go before UPDATEs within one flush.** Retiring an old row (`superseded = true`) and inserting its replacement in one flush violates `UNIQUE ... WHERE NOT superseded` even though the end state is valid, because the index is checked per statement. Flush the retirement first, then insert, then set the back-reference (an FK to the new id). `canonicalize.py`'s `_supersede` is the pattern; anything else that adopts the AD-6 supersession shape on a partially-indexed table inherits it.
- **A dry run with rollback over the real dev DB is the cheapest live verification for a canonicalization change.** `begin_nested()` → canonicalize → inspect → raise-to-rollback, per issuer. It found in one pass what the trimmed golden fixtures cannot see (they carry no amendment that disagrees with an original): under the new tier, 115 facts across CP/OTEX are now sourced from amendments and none changed a figure. It also showed, incidentally, that seven of nine filers on the dev DB were still at `concepts_v9` — the half-degraded-page state — which no test reports.
